# /phase-07-pos-core

Read `CLAUDE.md` §6, §9 before starting. This is the flagship screen — take the most care here. §9 sets the Indian/TN design point of view (dense + colorful, not minimalist; Indian ₹ number formatting; table number as the dominant visual anchor; item-code quick entry; bilingual-by-default staff grid) — every bullet below assumes it.

## Goal
The main POS billing screen: responsive across desktop/tablet/mobile per CLAUDE.md §9's per-device UX rules, full keyboard + touch + mouse support, fast item search plus numeric item-code entry, bilingual-by-default item labels, category tabs (led by a "Top Selling" tab), hold/recall bill.

## Scope
1. **Backend**
   - `POST /api/v1/orders` (create/update an in-progress order — this is the "cart" persisted server-side so Hold works across devices/sessions). Order carries `table_id` (nullable — null for non-seating sections) and `section_id`.
   - Effective item price resolution: for the order's current `section_id`, look up `item_section_prices` (item_id, section_id); fall back to `items.price` if no override row exists. `order_items.unit_price` is snapshotted at add-time — changing the item/section master later never retroactively changes an already-open/held order line.
   - Changing an order's table/section after items exist re-resolves prices for all lines and returns the recalculated totals for the frontend to confirm with the user before applying.
   - `GET /api/v1/orders?status=held` for recall list.
   - `GET /api/v1/items/search?q=` — fast fuzzy search across `name_en` + `name_ta` (Postgres trigram index — add migration).
   - `GET /api/v1/items/by-code/{item_code}` — exact-match lookup for the numeric item-code quick-entry field (§9); each item optionally carries a short `item_code` set in Phase 05's item master.
   - `GET /api/v1/items/top-sellers` to power the "Top Selling" category tab.
   - `GET /api/v1/sections/pos` — active seating sections for the POS table/section picker (used by Frontend below).
   - Order state machine: `open → held → billed` (billed transitions in Phase 09).
   - `POST /api/v1/orders`/`POST /api/v1/kot` (Phase 08) are reachable by `waiter`, `pos_user`, or `tenant_admin` — a waiter can build and send an order to the kitchen. Nothing in this phase's API surface finalizes a bill; that endpoint lives in Phase 09 and explicitly excludes `waiter` server-side (not just hidden client-side), per CLAUDE.md §5/§9.
2. **Frontend** (`/pos`)
   - **Desktop layout**: left category tabs (image if plan allows, per CLAUDE.md §6) + a dense item grid (smaller card padding, more items per row than a typical Western POS — per §9), right-side running order/cart. The first category tab is always **Top Selling**. A numeric item-code field sits beside search, auto-refocusing after every add/Enter so a cashier can move through a long order keyboard-only. This is the primary all-day billing-counter layout — keyboard shortcuts are first-class, not a secondary affordance.
   - **Tablet layout**: category rail moves from the left column to a horizontal strip across the top (a side rail leaves too little width once the cart panel is also on screen at tablet portrait sizes, per §9) — items and the running-order cart stay side-by-side below it. Still not the mobile flow: no bottom-sheet cart, no FAB, table/waiter selection stays visible alongside the order at all times, and the table/section and waiter selectors must be reachable in one tap without opening a modal, since tablet use is often standing/moving rather than seated at a fixed counter.
   - **Mobile layout**: single-column — category chips in a horizontally-scrollable strip across the top (Top Selling still first, same top-strip pattern as tablet), item list below, cart reached via a floating action button as a swipe-up bottom sheet with item count badge. The FAB and the sheet's primary actions are what's positioned for one-handed thumb reach on large-screen Android phones (§9), not the category strip. No overlapping elements; test at common phone widths. No item-code field (no physical keypad) — search-first with large touch targets. Show an explicit "Saving…/Saved" sync indicator on every cart mutation and queue add-item actions locally through a network blip rather than blocking the waiter (§9's network-tolerant rule).
   - **Billing action is role-gated, not device-gated (§5/§9)**: render the bottom sheet's primary action row from the logged-in role, not the breakpoint. `waiter` → **Hold** and **Add to KOT** only, no Bill button rendered anywhere in that session. `pos_user`/`tenant_admin` → Hold, KOT, and Bill, on every breakpoint including mobile (e.g. a counter phone). Same component on desktop/tablet — this isn't a mobile-only rule, mobile is just where a `waiter` session actually exists in practice.
   - Item cards/rows show **English name (primary line) + Tamil name (smaller secondary line) stacked together by default** on the staff-facing grid — this is not the `show_tamil_names` toggle; that setting only controls what prints on the KOT/customer bill (§9).
   - Prices and totals shown in Indian digit grouping (₹1,25,000 style, paise only when non-zero — §9).
   - "Full Meals / Half Meals / Mini Meals"-style combo items are flagged `is_combo_tile` in the item master (Phase 05) and render as larger, visually distinct tiles at the front of their category or in Top Selling, not same-size as a regular à la carte item (§9).
   - Table/section selector shows the table number **large and bold, with its section as a smaller badge alongside** (e.g. big **"T5"** + small `AC` badge — §9's table-prominence rule), not the reverse; non-seating sections (Takeaway, Online Delivery) appear as directly-selectable chips with no table number. Switching section/table after items are already in the cart shows a recalculated-totals confirmation (per the backend re-resolution above) before applying. The same table-number-dominant styling carries through to the cart header.
   - Item prices shown in the grid/cart reflect the resolved price for the order's current section (Pro+; Lite always shows the flat base price since it has no section pricing).
   - **Low-stock/out-of-stock item state** (CLAUDE.md §11, backed by Phase 08's `track_inventory`/`available_qty`): for a tracked item, the grid card itself (not a popup) shows a small "N left" badge once `available_qty <= 5`; at `available_qty = 0` the whole card greys out and stops responding to tap/click/item-code entry (attempting the item-code shortcut for an out-of-stock item is a no-op with a brief inline "out of stock" hint, not a silent failure). The POS screen holds open the same `/ws/location/{location_id}` connection Phase 08 defines, consuming only `item_stock` messages (ignoring `kot_ticket` ones) — so a KOT sent from a *different* device (e.g. a waiter's phone) updates this grid's badge/greyed state live, not just on next load. Untracked items (the vast majority — this is opt-in per item) render exactly as before, no badge.
   - Keyboard shortcuts: F-keys jump categories (Top Selling first), next two F-keys cycle table/section and waiter, Ctrl+K focuses search, item-code field + Enter adds by code, Enter adds the highlighted item, Ctrl+H hold bill, Ctrl+P print, Ctrl+Enter send KOT.
   - Touch-friendly large tap targets on tablet/mobile; item cards show qty stepper.
   - Hold Bill button (saves order as `held` with an optional label/table number) and Recall Bill panel/modal (searchable list of held orders); a held bill retains its table/section AND waiter assignment on recall.
   - **"KOT Tickets" popup** (small button near Hold/Recall, `pos_user`/`tenant_admin` only, CLAUDE.md §11): opens a list of every currently open ticket across the location — sourced from Phase 08's `GET /api/v1/kot/tickets/active` — shown as ticket number + table/section, newest first. This is the primary way a cashier picks up an order a *different* user (a waiter, on mobile) already sent to the kitchen: selecting a row loads that order into the billing screen exactly like Recall does. Distinct from Recall Bill, which is for a cashier parking their *own* in-progress order — both ultimately load an order into the cart, but the entry point and mental model differ (Recall = "I'll finish this myself later", KOT Tickets = "someone else already started this"). Once that order is billed (Phase 09), it disappears from this popup automatically — no client-side bookkeeping needed, it's the same status filter as the query itself.
   - Waiter/table assignment selectors at the top of the order panel (uses Phase 06 data). A `pos_user`/`tenant_admin` login can assign any waiter; a `waiter` login auto-locks the selector to themself so every bill they ring up is attributed correctly with no extra step. There is no separate "cashier select" — the cashier-of-record is always whichever `pos_user` is logged in and rang up the bill (mirrors the waiter auto-lock pattern); if `tenant_admin` operates the POS directly, no cashier incentive is attributed for those bills.
   - The bill summary shows two live incentive lines: waiter (`waiter.incentive_rate` × net sale value) and cashier (`pos_user.incentive_rate` × net sale value, when the logged-in user is a `pos_user`) — both informational for staff/reporting, never added to the customer-facing total or the printed bill.
   - Payment method buttons in the bill summary/checkout list **UPI before Cash before Card**, with a generic "UPI" badge (§9) — same visual weight as Cash/Card, not a smaller secondary option.

## Acceptance Criteria
- Same order flow fully usable with only keyboard, only touch, and only mouse.
- Mobile viewport (e.g. 390px, 428px widths) shows no overlapping/cut-off UI.
- Hold → navigate away → Recall restores the exact cart state, including table/section and waiter assignment.
- Item search returns results in <300ms perceived latency for a 500-item catalog (trigram index doing its job); typing a valid item code + Enter adds that item with the same latency budget.
- Selecting a table shows its section next to the table number; adding an item priced differently for that section shows the section price, not the base price (Pro+ tenant test); a Lite tenant always shows the flat base price regardless of section.
- Changing a bill's table from one section to another (e.g. Non-AC → AC) after items are already added recalculates and confirms new totals rather than silently changing them.
- Item grid shows English + Tamil name together on every card regardless of `show_tamil_names`; toggling that setting only changes the KOT/bill print output (verified against Phase 08/09), not the staff-facing screen.
- A combo/thali item marked `is_combo_tile` renders visibly larger than a regular item card in the same category.
- A `waiter` login (any breakpoint) never renders a Bill/print/payment control — only Hold and Add to KOT are visible.
- A `pos_user` opens the "KOT Tickets" popup, sees a ticket a waiter fired from mobile (ticket no + table), selects it, and bills it; the ticket then no longer appears in the popup for anyone.
- A tracked item at `available_qty <= 5` shows its "N left" badge on the card itself; at 0 the card is visibly greyed and neither tap, click, nor its item-code shortcut adds it to the cart.
